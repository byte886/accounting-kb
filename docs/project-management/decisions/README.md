# 架构决策记录（ADR — Architecture Decision Records）

> **文档类型**：Concept（概念说明）
> **更新频率**：结构变更时
> **维护者**：AI自动维护
> **读者**：AI代理+人类

> 本文档记录项目中的重要决策及其背景、原因和后果。
> 每次做出影响项目结构、流程、工具选择的重要决策时，按模板记录。

---

## 什么是ADR

ADR是一种轻量级的决策记录方式，帮助AI和人理解"为什么这样做"，而不仅仅是"做了什么"。

**每个ADR包含**：
- 状态（已采纳/已废弃/待定）
- 背景（为什么需要做这个决策）
- 决策（具体做了什么）
- 后果（正面/负面/后续）
- 参考（决策依据的来源）

## 何时记录ADR

**核心原则：只记录对项目有长期影响的重要决策，对项目过后没有影响的内容不用记录。**

**判断标准**：这个决策在3个月后是否仍然影响项目的运作？
- 是 → 需要记录ADR
- 否 → 不需要记录ADR，只需要在CHANGELOG或任务报告中记录

**必须记录ADR的场景**（对项目有长期影响）：
1. 项目目录结构重大调整
2. 核心工具/技术栈变更（如转写方案从FunASR切换到faster-whisper）
3. 工作流重大变更（如做题流程从ref点击切换到JavaScript直接点击）
4. 存储分工变更（如视频存储位置变更）
5. 知识库组织结构变更
6. 项目重命名（仓库名、目录名、项目名称）
7. 静态/动态内容分离等架构级决策

**不需要记录ADR的场景**（对项目过后没有影响）：
1. 小问题修复（文档链接错误、脚本bug）
2. 单个文档内容更新
3. 临时操作
4. 单次任务的执行细节
5. 不影响后续工作的优化调整

## ADR模板

```markdown
# ADR-XXX: 决策标题

## 状态
已采纳/已废弃/待定（日期）

## 背景
为什么需要做这个决策？当前的问题是什么？

## 决策
具体做了什么？列出关键变更点。

## 后果
### 正面
### 负面
### 后续

## 参考
决策依据的来源（文档链接、搜索结果等）
```

## 维护规则

1. **新增ADR时**：在本索引表格中添加条目，文件命名为 `ADR-XXX-简短标题.md`
2. **废弃ADR时**：不删除文件，在状态中标注"已废弃"，并在文件开头说明废弃原因和替代方案
3. **ADR编号递增**：不重复使用已废弃的编号
4. **定期检查**：每次大阶段完成后，检查是否有重要决策未记录
