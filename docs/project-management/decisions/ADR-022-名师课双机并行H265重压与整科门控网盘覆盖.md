# ADR-022: 名师课 H.265 重压的双机并行分工、常驻保活与整科门控网盘覆盖

> **文档类型**：Active（决策记录）
> **更新频率**：决策变更时
> **维护者**：AI 自动维护 + 用户审核
> **读者**：AI 代理 + 人类

## 状态

已采纳并运行中（2026-09-15 部署双机链路，2026-09-16 用户按忙闲多次调档确认）。审计、战略两科已全量 hevc 上云并通过终态核验（零差异）；经济法、税法（本机）与会计、财管（目标机）在途压缩，压完按本 ADR 的门控自动覆盖上云。本 ADR 不改变 ADR-002 的压缩参数、ADR-005 的四地存储分工、ADR-020 的网盘分库与沙箱根名、ADR-021 的数据实体形态，只解决"单机压不完、长跑会停、hevc 如何安全替换网盘早期 h264"三件事。

## 背景

- 名师课六科共约 2062 个 `*_video.mp4`、约 1TB 的未压缩 H.264 1080P（采集时 `-c copy` 封装，见 ADR-018）。单机单实例 libx265 实测 speed≈6.3x，全部压完约需 8 天连续运行。
- 用户另有一台 macOS（16 逻辑核，数据在外置机械盘 `/Volumes/backup`，HFS+），与本机同一局域网、可 `git clone` 公有仓，具备双机并行缩短工期的条件。
- 早期（决定统一重压前）已向百度网盘传过一轮 **h264 原片**做备份；hevc 重压推进后，需要用 hevc 同名覆盖网盘 h264，但绝不能在一科尚未全部压完时把 h264 混传上去。
- 本机长跑最初用 `nohup`，2026-09-15 夜间随启动它的 Doubao 会话关闭被连带 KILL（`nohup` 只挡 SIGHUP、挡不住会话进程组清理），压缩/上传/看门集体停摆约 6h，暴露"保活必须与会话无关"。

## 决策

### 1. 双机科目零重叠分工 + 数据 rsync 迁移

- **本机（20 逻辑核，项目主存储所在）负责：审计、战略、经济法、税法**；**目标机（16 逻辑核 + 外置机械盘）负责：会计、财管**。两台科目互不重叠，从两端推进，避免同一文件双写分叉。
- 代码/文档由目标机 `git clone` 公有仓获得；**课程数据不走 git（gitignore）**，由本机经局域网 `rsync -az` 推到目标机**完全同构的相对路径** `data/高顿/CPA/【VIPCPA专享】名师专业课-<科>/...`，脚本里一律相对路径访问。
- 目标机 ffmpeg/ffprobe 在 `/usr/local/bin`、python 用 `/usr/local/bin/python3`（系统自带 3.9 仅兜底）；远程命令先 `export PATH=/usr/local/bin:$PATH`。
- **闭环（批 1 收尾）**：目标机压完的 hevc 要 `rsync` 回传本机主存储同名覆盖留档，避免本机留 h264、目标机留 hevc 的长期分叉；回传并核验后再删目标机已回传文件以滚动腾空间。

### 2. 压缩参数不变，驱动补 `--jobs` / `--reverse`

- 参数沿用 ADR-002：libx265 / CRF30 / preset fast / AAC 96k / `-tag:v hvc1` / faststart，"能基本看清课件文字"，**不走抽音频方案**。
- `code/scripts/compress_ep3_videos.py` 新增：`--jobs N`（x265 `-x265-params pools=N:frame-threads=4:wpp=1`）、`--reverse`（倒序遍历，配合两台从两端推进）。原有幂等不变：压前 ffprobe 读 v:0 编码、已是 hevc 跳过；写同目录 `.compress_tmp__` 临时文件，验证（hevc / 分辨率不变 / 时长容差 max(3s,0.1%) / 可解析）通过才 `os.replace` 同名覆盖，失败删临时文件、保留原片；`fcntl.flock` 占 `data/_workspace/_account/ep3/compress.lock` 保证单实例。

### 3. 保活：本机 launchd 总管，目标机 nohup 看门

- **本机**部署 launchd LaunchAgent `~/Library/LaunchAgents/com.gaodun.ep3-local-supervisor.plist`（RunAtLoad + `KeepAlive{SuccessfulExit=false}`），常驻跑 `code/scripts/ep3_local_supervisor.sh`：每 120s 巡检，无压缩进程且仍有 h264 就拉起压缩，按门控拉起上传，全部科目 hevc 且上传成功后 `exit 0`（正常完成不重启、异常被杀才自愈）。launchd 环境 PATH 仅系统目录，脚本内必须自行 `export PATH=/usr/local/bin:$PATH`。
- **目标机不跑 Doubao**，用两个 `nohup caffeinate -dimsu bash logs/target_*watch.sh` 看门（经 14h+ 验证可靠）：`target_compress_watch.sh` 负责会计→财管压缩衔接，`target_netdisk_watch.sh` 负责全 hevc 后限速上传。两台均 `sudo pmset -a sleep 0 disksleep 0 disablesleep 1`（任务结束需恢复默认）。

### 4. 按忙闲动态调档，改档即重启、幂等续压

- `--jobs N` 随用户忙闲动态调整（参考档：本机 20 核白天 8 / 闲时 12–13 / 夜间 17；目标机 16 核 + 外置 IO 白天 6 / 闲时 9–11，外置机械盘 IO 是瓶颈、超过约 11 后 ffmpeg 吃不满核、收益递减）。具体档数是易变值，以当时现场负载为准，不固化。
- 改档流程：改脚本里的 `JOBS` → 本机 `launchctl unload/load` 总管、目标机 kill 看门与压缩后重启看门 → 清 `.compress_tmp__*` → 压缩幂等续压（只中断当前一个文件）。**改档后约 2–4 分钟（ffprobe 全量 probe）才重新拉起压缩，属正常自愈，不要在这段时间反复 reload 观察。**

### 5. 网盘"整科全 hevc 门控 + 清旧 done + rtype=3 覆盖"

- **一门课必须全部视频为 hevc（ffprobe 非 hevc 计数=0）且压缩进程已结束，才允许上传该科视频**；压缩在跑时绝不探测/上传，从机制上杜绝 h264 混传。`sync_ep3_ready.sh` 的 ready_filter 只挑"完整讲"（meta 与非空视频齐备）、**不判编码**，故编码门控在总管/看门一侧。
- 某科全 hevc 首次上传前执行 `reset_videos_done_once`：删除该 profile `data/_workspace/<profile>/logs/netdisk_done/` 下所有**非 `notes__` 前缀**的视频 done 标记（保留讲义标记），强制 hevc 全量重传、`rtype=3` 同名覆盖网盘早期 h264；每科只清一次（`<prof>.videoreset` 标志）。done 文件名前缀是**阶段名**（如"全面精讲"）而非字面"videos"，仅讲义那次前缀为 `notes__`。
- **两台各自上传、互不干扰**（目标机会计/财管的 done 与看门在目标机本地）；每台讲并发=1、`BAIDU_UPLOAD_RATE=1000k`（仅分片 curl 限速，list/mkdir 小请求不限），两台加总 ≤2MB/s，不占满上行、不挤其它应用。

### 6. 网盘真实状态以终态核验为准，不信 done 标记

- done 标记只反映"某次上传动作完成"，不证明网盘当前就是 hevc。权威核验用 `code/scripts/verify_netdisk_final.py <本地课程根> <网盘课程根>` 递归比对目录/文件集合与**字节大小**（rc=0 才一致），`code/scripts/netdisk_verify_summary.py` 分类汇总。
- 网盘文件无法 ffprobe，识别"网盘残留 h264"靠大小：本地 hevc 显著小于 h264（实测样本约 1/13），核验输出"大小不一致且网盘更大"即旧大版，需 reset 后覆盖重传。

## 关键校验记录（2026-09-16）

- 审计 257 讲、战略 129 讲已全量 hevc 上云；22:43/22:45 两次终态核验 `rc=0`，视频 0 缺失 / 0 大小不一致 / 0 旧大版、讲义 0 差异。
- 目标机会计 607、财管 354（共 961 个 mp4）与本机源**逐一同名 diff 完全一致**（无遗漏/多余/0 字节），961 个 ffprobe 全部可正常解析（h264 568 / hevc 393，合计 536.5h），抽样实解码（会计 hevc/h264、财管 h264）均通过。
- 战略曾**不在**本机总管上传循环（循环只列了审计/税法/经济法），实际靠 2026-09-15 早期流程传齐 hevc（含补传的最后 3 讲）并经核验零差异；新增/调整负责科目时，必须同步纳入自动覆盖清单，不能依赖一次性补传。

## 后果与踩坑（操作细节见两份 SOP）

**正面**：双机把约 8 天的单机压期压缩到约 2 天量级；launchd 总管与会话解耦后夜间不再静默停摆；整科门控 + 清旧 done + rtype=3 保证网盘最终只留 hevc 母带且不产生 `_时间戳` 改名副本；终态核验提供可复算的交付证据。

**必须记住的坑**：

1. `launchctl unload` 总管会**连坐杀死**它 nohup 拉起的压缩子进程（同一 launchd job 进程组）——压缩在跑时不要为观察而 reload。
2. 禁用 `pkill -f` / `pgrep -f <脚本> | xargs kill`：模式串会出现在命令自身命令行里导致自杀（exit 137）。可靠做法是按进程组排除当前 shell（`PGID=$(ps -o pgid= -p $$)` + `ps -axo pid,pgid,command | awk -v g=$PGID '$2!=g&&/正则/{print $1}'`）。
3. 上传链路 `sync_course_netdisk.sh` 用 `xargs -P` 派生，父 bash 被杀后子进程成**孤儿被 launchd 收养继续派生**；清理须分层：顶层 sync → 孤儿 xargs / `bash -c`（按 upload_one 匹配）→ upload_course/baidu_upload → curl，连续两轮计数 0 才算根除。
4. 目标机是 bash 3.2：`"$JOBS"` 后紧跟中文全角括号会被吞进变量名、在 `set -u` 下触发 unbound variable；用 `${JOBS}` 定界，看门日志文案用 ASCII。
5. 临时压缩文件名 `.compress_tmp__<老师>_video.mp4` **以 `_video.mp4` 结尾**，`rglob('*_video.mp4')` 会把它计入（曾把会计 607 误报成 608）；任何统计/遍历必须排除 `.compress_tmp`。
6. `sync_course_netdisk.sh` 无论成败都固定打印"失败讲（…）:"标题，**真正失败行才是行首恰好 3 个空格 + `- `**；判定成功不能 grep 标题（恒为假会导致空转重拉、永不 mark_done），要 `! grep -qE '^[[:space:]]{3}- '`。
7. 统计编码必须用 python subprocess + 线程池并发 ffprobe 取 `v:0 codec_name`；不要用 `xargs -I{}` 批量 ffprobe 中文超长路径（command line too long，曾误报编码数）。

## 演进注记（2026-09-17）：整科门控 → 按科滚动、限速 1000k→1100k、进程检测精确化

> 本节只记录从原决策（上文第 5 节）到现机制的演进，原文保留不改；现行操作以 finalize-sop 步骤 1 与 concept `workflow-netdisk-hevc-sync` 更新后的措辞为准。

1. **门控放宽为「按科滚动」**：原第 5 节要求"整科全 hevc **且压缩进程结束**才传"，但本机一个 `compress --course 税法 --course 经济法` 进程同时排两科，导致已压完的经济法要干等税法（约 30h）才上云。实测上传走网络（已限速）、压缩吃 CPU、目录按 profile 隔离，二者资源不冲突，故改为**按科门控**：某科全 hevc 且当前没在压该科即可传该科，可与另一科压缩并行；整机一次仍只传一科（互斥）。"在压该科"判据：本机看该科 videos 下有无 `.compress_tmp*`（一个 compress 进程可带多个 `--course`，不能只看进程名）；目标机看门本就按 `pgrep --course <科>` 判断，天然按科。
2. **限速科学定值 `1100k`**：`networkQuality -s` 实测两台共享出口上行 **34.6 Mbps（≈4.3 MB/s）**，上行满载响应评级 **Low（延迟 1.50s、40 RPM，缓冲膨胀严重）**。为不影响豆包/交互，持续上传合计压在上行约 50%：两台对等各 `BAIDU_UPLOAD_RATE=1100k`（≈1.1 MB/s），同时传最坏合计 ≈18 Mbps、占上行 ~52%。原 `1000k`（两台合计 ~47%）本就合理，`1100k` 是安全上限，再高会重现秒级卡顿。
3. **进程检测精确化（新坑）**：总管/看门判断"在跑"必须匹配带解释器前缀的真进程——`pgrep -f 'python3 .*compress_ep3_videos\.py'`、`pgrep -f 'bash .*sync_ep3_ready\.sh'`。裸 `pgrep -f 脚本名` 会把命令行里仅出现该脚本文本的 grep / 外层 shell（含运维查询命令本身）误判为"在跑"，导致漏拉压缩（本次 reload 后首轮即因此空跳，靠次轮巡检自愈，改精确匹配后根除）。
4. 当日实测：reload 后本机进入"压税法（jobs13）+ 传经济法（1100k）"并行，目标机"压会计（jobs11）+ 看门等会计完按科传"并行；经济法 hevc 上云终态仍以 `verify_netdisk_final.py` 核验为准（在传，未终验）。
