# ADR-010：浏览器自动化连接通道与技术栈选型（Puppeteer/CDP 主、Playwright 扩展备）

> **文档类型**：Active（过程记录 — 架构决策记录）
> **日期**：2026-09-01
> **状态**：已采纳
> **决策者**：用户 + AI（开发工程师角色）

## 背景

「自动做作业」链路现状为 **Playwright CLI 扩展模式（Extension relay）操作页面 UI**。历史做题统计（10 卷 73 题，知识命中率 93.2%，失分集中在多选交互）表明：**瓶颈在 UI 执行链路的不确定性，而非答案知识**——同一套卷重复做，正确率在 100%～50% 间跳变；新题或页面步骤稍有差异就出现未覆盖分支；交互流程写得越细越长越僵化，无法穷举分支。

优化方向是「**接口为主、UI 兜底**」：优先直接走取题/交卷/解析接口，接口未命中再退回 UI。实现这一方向的前提，是先选定一条浏览器连接通道，同时满足：

1. **复用用户日常 Chrome 的现有登录态**（不重新登录、不另建独立 Profile、不重启 Chrome）；
2. 具备**完整的 CDP 网络能力**（抓取全部请求/响应、能在页面上下文发请求、能驱动页面）；
3. 授权/连接过程尽量**自动化、稳定**。

现状的 Playwright **扩展模式下 CDP 被禁用**（`CDP Not allowed through extension`），无法满足第 2 点，因此需要重新选型。本 ADR 只决策「连接通道与自动化技术栈」，不涉及具体做题业务改造。

## 决策

1. **连接层采用 `puppeteer-core`，经 Chrome 144+ 的「运行时远程调试」通道（`chrome://inspect/#remote-debugging`）连接用户正在使用的日常 Chrome（默认 Profile）**，复用现有登录态，免重启、免独立 Profile、免重新登录。
2. **授权弹窗自动化**：每次新连接 Chrome 弹出「要允许远程调试吗？」时，由 macOS 辅助功能（AX）对「允许」按钮执行元素级 `AXPress` 代点；连接模块在整个连接/重试周期持续代点，并对偶发的握手 403 做有限次退避重试。
3. **技术栈分层主备**：
   - **主链路**：`puppeteer-core`/CDP——网络抓包、页面内 `fetch` 取题/交卷（自动携带 Cookie 与前端签名，零逆向）、提交后回查、请求快照留痕；
   - **兜底链路**：保留现有 Playwright 扩展 UI 脚本（`answer_option.sh`/`answer_multi.sh`/`submit_exam.sh`），接口未命中或异常时用 UI 保证「作业一定交得上」；
   - 两者可同时挂在同一个 Chrome，互不冲突。
4. **依赖管理**：Node 依赖由仓库根 `package.json` 声明（`puppeteer-core`，不下载 Chromium）；`node_modules/` 不入库（.gitignore 已忽略），新环境在仓库根执行 `npm install` 即可补足。

## 备选方案

连接「日常 Chrome（默认 Profile、不重启）」这一约束下，各方式均经本机实测或官方资料核实：

| 连接方式 | 复用日常登录态 | 实测/核实结果 | 结论 |
|---|---|---|---|
| Playwright CLI `attach --cdp=chrome` | 是 | 把端点解析成**不带 UUID** 的 `/devtools/browser`，30s 超时 | 弃用 |
| playwright-core `connectOverCDP`（带 UUID） | 是 | WebSocket 已连接但等不到协议消息、超时；官方 issue #40027 确认该问题到 v1.60 才着手支持 | 弃用（留再评估钩子） |
| 裸 CDP（Node 内置 WebSocket + `Target.setAutoAttach`） | 是 | 可行，实时抓到请求/响应，但 target 会话、事件封装全要手写，代码量大 | 作为原理与保底 |
| **`puppeteer-core.connect({browserWSEndpoint: 带UUID})`** | 是 | **稳定连通，`page.on('request'/'response')`、`evaluate`、`reload` 全部正常**；官方 `handleDevToolsAsPage` 选项专门兼容该通道 | **采用** |
| `puppeteer.connect({channel:'stable'})` 自动发现端点 | 是 | 实验性选项，本环境 connect 下报 `path ... undefined` | 暂不采用 |
| chrome-devtools-mcp（`--autoConnect`） | 是 | 面向 AI 宿主的 MCP 交互层（stdio→Puppeteer→CDP，多两层），适合开发期交互勘察，不适合无人值守运行时 | 不进生产 |
| Playwright 扩展模式（现状） | 是 | UI 操作可用，但 CDP 被扩展禁用 | 保留为 UI 兜底 |
| 命令行 `--remote-debugging-port` + 独立 Profile | 否（需独立 Profile、首次登录） | Chrome 136+ 对默认 Profile 屏蔽该参数，必须非默认 user-data-dir | 不符合约束 |

## 决策理由

1. **唯一同时满足三前提的稳定方案**：只有 Chrome 144+ 运行时通道能在「不重启、不独立 Profile、不重登」前提下暴露完整 CDP；而在该通道上，`puppeteer-core` 是官方与实测双重确认可用的高级库（chrome-devtools-mcp 内部同样用 Puppeteer），Playwright 当前版本仍不稳定。
2. **开发成本显著低于裸 CDP**：Puppeteer 封装了 target 自动 attach、会话路由、网络事件、`evaluate`/点击/等待，业务代码量比手写 CDP 小一个数量级；裸 CDP 探索过程保留为理解基础与极端情况保底。
3. **契合「接口为主、UI 兜底」**：接口化后绝大多数操作不再模拟点击，从根上消除选择器失效、时序等待、页面分支差异等当前波动源；少量未覆盖场景仍由成熟的 Playwright UI 兜底，主备分层而非重复实现。
4. **授权自动化有官方依据且无安全副作用**：Chrome 维护者明确「只在用户显式同意时接受连接」是刻意设计，不提供永久免确认；以 AXPress 自动完成「显式同意」动作等价于用户本人点击，且仅作用于本机回环端口。
5. **依赖可迁移、可恢复**：`package.json`/`package-lock.json` 入库锁定版本，`node_modules` 不入库；新环境 `npm install` 一键补足，缺依赖时连接模块会打印明确恢复指令。

## 后果

### 正面
- 获得复用日常登录态的完整 CDP 能力，为接口化取题/交卷/回查铺路；
- 连接、授权、重试、抓包沉淀为可复用模块（`code/scripts/cdp/`），后续业务直接调用；
- 不推翻现有 Playwright UI 资产，风险可控、可灰度替换。

### 负面 / 代价
- 引入 Node 依赖 `puppeteer-core`（很轻，不下载 Chromium）与 macOS「辅助功能」授权前置；
- 绑定 Chromium 系（本项目只用 Chrome，无影响）；
- 依赖 Chrome 144+ 运行时调试通道这一较新特性，未来 Chrome 若调整协议需跟进（已记录官方检索入口，便于复核）；
- 每次连接仍会弹授权窗（由脚本自动点掉），无法从设置层面永久关闭。

### 后续
- 决策点②：在本通道上回到「取题/答案来源/鉴权重放/提交风控/学习闭环」的方案评估与选型；
- 跟踪 Playwright issue #40027，若其后续版本对该通道稳定支持，可再评估是否统一回 Playwright；
- 接口档案与本地题库的 schema 设计（决策点③）、PoC 范围与替换上线顺序（决策点④）另行评审。

## 验证（2026-09-01，本机）

- 环境：Chrome 152（CDP product 151.0.7922.174，protocol 1.3）、Node v22.23.2、puppeteer-core 25.9.0、Playwright CLI 1.62.1、macOS；
- `node code/scripts/cdp/connectBrowser.js` 自检：自动 AXPress 授权，约 1.4～3.6s 连上日常 Chrome，正确读取现成标签后干净断开、保留页面；
- 连续 4 次连接全部成功（内置退避重试吸收偶发 403 竞态）；
- 抓包：attach 现成百度标签 reload，实时见 93 个请求；`sniff_demo.js` 过滤静态噪音后记录 57 条、输出 115 行请求/响应 JSONL。
