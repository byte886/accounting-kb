# 项目状态查询协议（Project Status Query Protocol）

> **文档类型**：Governance（治理规范 — AI查询协议）
> **更新频率**：每次新增查询类型或发现新的模糊表达时
> **维护者**：AI自动维护 + 用户审核
> **读者**：AI代理（收到用户模糊查询时必须参考）

本文档定义项目状态查询的标准化协议，解决"用户表达不太准确时AI可能误会"的问题。通过定义查询意图分类、模糊表达映射表、标准响应格式，让AI能准确理解用户意图。

## 零、常用查询话术速查表（直接复制使用）

### 🛠️ Q7 项目维护检查（执行型：真去检查并出报告/修复）

> **与 Q3 的区别**：Q3 是"问"有哪些维护（只回答清单，只读）；**Q7 是让 AI 实际动手做检查**。想让 AI 真正扫描、分级、修复、出报告时用这一类，话术里要带"检查 / 体检 / 维护一下 / 出报告"等动作词。

| 你想要 | 直接复制这句话 |
|--------|----------------|
| 一句话做维护 | `以项目架构师身份，对项目做一次维护检查：目录结构一致性+文档健康度，出检查报告` |
| 结构+规范标准检查 | `以项目架构师身份做项目维护：1)对照DIRECTORY_STRUCTURE查目录/文件归属/空目录/.gitignore并跑check_directory_structure.sh与check_naming_consistency.py；2)按DOCUMENTATION_OPTIMIZATION第十二章11项清单查文档登记、类型标注、断链、文档孤岛、内容重叠、超长文档、口径与命名。小问题直接修，结构性问题先问我` |
| 只体检不改 | `以项目架构师身份做只读体检，不改任何文件：跑结构脚本+11项清单全量扫描，问题按"可直接修/需决策"分级，标位置和依据，等我确认` |
| 只查目录结构 | `以项目架构师身份检查目录结构一致性：对照DIRECTORY_STRUCTURE.md并跑check_directory_structure.sh，列出不一致项` |
| 只查文档规范/内容 | `以项目架构师身份做文档健康度检查：按11项清单查完整性/关联性/质量/规范，出报告` |
| 在旧报告上增量查 | `在最近一份文档健康度检查报告基础上做增量检查，只报变化和新增问题` |

## 三、AI响应协议

### 3.1 意图识别流程

当收到用户查询时，AI必须按以下流程处理：

1. **识别意图**：根据模糊表达映射表，判断用户的查询属于哪一类（Q1-Q7）
2. **如果意图不明确**：主动询问用户想了解哪方面，给出2-3个选项，而不是猜测
3. **如果映射到多个意图**：询问用户想优先了解哪方面
4. **读取对应文档**：根据意图，读取对应的权威文档
5. **结构化响应**：按标准响应格式回答

### 3.2 标准响应格式

**Q1 任务状态查询的响应格式：**
```
## 当前任务状态

### 正在进行
- [任务1]：进度XX%，预计完成时间
- [任务2]：进度XX%

### 待开始
- [任务3]：前置依赖是什么
- [任务4]：预计开始时间

### 已完成（最近）
- [任务5]：完成时间，产出物位置

### 下一步
- 立即要做的事
```

**Q2 问题/BUG查询的响应格式：**
```
## 当前问题/BUG清单

### 未解决
- [问题1]：严重程度，影响范围，当前状态
- [问题2]：严重程度，影响范围，当前状态

### 已解决（最近）
- [问题3]：解决时间，解决方案

### 潜在风险
- [风险1]：发生概率，影响范围
```

**Q3 维护工作查询的响应格式：**
```
## 维护工作清单

### 定期维护（按周期）
- [每日/每周/每月]：维护内容，检查方法

### 待优化项
- [优化1]：优先级，预计工作量
- [优化2]：优先级，预计工作量

### 最近完成的维护
- [维护1]：完成时间，效果
```

**Q4 文档/操作查询的响应格式：**
```
## 相关文档和操作

### 直接相关的文档
- [文档1]：路径，简要说明
- [文档2]：路径，简要说明

### 操作步骤
1. 步骤1
2. 步骤2
3. 步骤3

### 注意事项
- 注意点1
- 注意点2
```

**Q5 项目概览查询的响应格式：**
```
## 项目概览

### 项目目标
一句话说明项目目标

### 当前阶段
- 阶段名称，完成度XX%

### 关键指标
- 已完成课程：X/Y
- 知识库章节：X个
- 已验证试卷：X套

### 最近进展
- 最近完成的重要事项

### 下一步重点
- 接下来1-2周的重点工作
```

**Q6 决策/历史查询的响应格式：**
```
## 相关决策/历史记录

### 直接相关的决策
- [ADR-XXX]：决策标题，状态，日期
  - 背景：...
  - 决策：...
  - 后果：...

### 相关历史记录
- [报告1]：路径，日期，简要内容

### 参考文档
- [文档1]：路径
```

**Q7 项目维护检查（执行型）的执行流程**（不是返回一段文本，而是动手执行）：
```
1. 先读 AGENTS/README/TASK_STATUS，以及 PROJECT_STRUCTURE_MAINTENANCE、DOCUMENTATION_OPTIMIZATION 第12章、DIRECTORY_STRUCTURE
2. 结构与命名检查：运行 scripts/check_directory_structure.sh，对照 DIRECTORY_STRUCTURE 查文件归属、空目录、.gitignore；运行 scripts/check_naming_consistency.py（--regression）查类型↔命名一致性、中文分隔符与相对断链
3. 文档健康度：按11项清单逐项查 完整性/关联性/结构/质量/维护；所有结论来自实际扫描或复算，不凭对话记忆
4. 问题分级：小问题（断链、过时数字、漏登记）直接修；结构性/拿不准的（目录改名、流程或hook变更、文档拆分）列方案先问用户；用户要求"只读/体检"则一律不改
5. 改后用不同方式复扫验证（重跑脚本、断链扫描），确认无回退、无新增问题
6. 需要留痕时在 data/_workspace/<course>/task-reports/ 按需生成《文档健康度检查报告_日期》（验证默认并入任务报告、不单独成文）；若只是对话内体检、结论已直接落回活文档，则按 PROJECT_STRUCTURE_MAINTENANCE 1.2 去留判据不必另留过程报告。无论是否出报告，都同步 CHANGELOG / DOCUMENTATION_MAP / TASK_STATUS
7. 按 git-workflow 8.3 分场景提交（治理等用户验收，日常及时 commit，push 按约定），提交前展示改动清单
```

## 四、意图不明确时的澄清话术

当AI无法确定用户意图时，应使用以下话术主动澄清：

**模板：**
```
我理解你可能想了解以下几个方面，请问你想优先了解哪一个？
1. [选项1，对应Q1]：简要说明
2. [选项2，对应Q2]：简要说明
3. [选项3，对应Q3]：简要说明
```

**示例：**
```
我理解你可能想了解以下几个方面，请问你想优先了解哪一个？
1. 任务状态：还有哪些任务要做、当前进度
2. 问题/BUG：有什么待解决的问题或异常
3. 维护工作：有什么待优化或需要定期检查的
```

## 五、维护规则

1. **新增查询类型时**：在第一节"查询意图分类"中添加新的意图ID和说明
2. **发现新的模糊表达时**：在第二节"模糊表达→意图映射表"中添加映射
3. **响应格式需要调整时**：在第三节"AI响应协议"中更新标准格式
4. **定期检查**：每次大阶段完成后，检查映射表是否覆盖了用户常用的表达
5. **AI必须遵守**：收到用户查询时，必须先参考本文档识别意图，再读取对应文档，按标准格式响应
