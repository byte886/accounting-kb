# 第一部分：文档优化流程（强制）

## 一、问题背景

在 AGENTS.md 优化过程中，发现了执行方式的问题：
- 采用了"逐步优化"的方式，每次只优化一部分
- 没有充分利用已有的最佳实践文档（`agents-md-best-practices.md`）
- 很多问题需要用户指出后才意识到，而不是主动分析发现

**根本原因**：有了好的指导文档，但在执行时没有严格按照文档来，而是凭经验逐步优化。

---

## 二、文档优化的正确流程（强制）

**执行任何文档优化任务时，必须按以下流程操作：**

### 第一步：读取相关最佳实践文档

在开始优化前，必须先读取相关的最佳实践文档：
- AGENTS.md 优化 → 读取 `docs/development/guides/agents-md-best-practices.md`
- README.md 优化 → 读取软件工程中 README 写作最佳实践
- 其他文档优化 → 读取相关的写作规范或最佳实践

### 第二步：基于文档进行一次性全面分析

**禁止逐步优化**。必须基于最佳实践文档，对目标文档进行一次性全面分析，列出所有不符合的地方：

```
分析清单示例（基于非可推断测试）：
1. 哪些内容已在其他文档中存在？→ 应该删除，只链接
2. 哪些内容是技术选择而不是禁止事项？→ 应该移到专项文档
3. 哪些内容是标准约定，AI已经知道？→ 应该删除
4. 哪些内容是不言而喻的建议？→ 应该删除
5. 哪些内容是频繁变化的？→ 应该移到活动状态文档
6. 哪些内容是给人看的项目介绍？→ 应该移到 README.md
```

### 第三步：一次性执行所有优化

基于分析结果，一次性执行所有优化，而不是逐步优化。

### 第四步：优化后主动验证

优化完成后，必须主动对照最佳实践文档检查：
1. 是否还有遗漏的不符合项？
2. 是否有新引入的问题？
3. 文档长度是否合理？
4. 章节结构是否清晰？

**禁止等待用户指出问题**，必须主动验证。

---

## 三、常见错误与纠正

| 错误做法 | 正确做法 |
|----------|----------|
| 逐步优化，每次只改一部分 | 一次性全面分析，一次性执行所有优化 |
| 凭经验优化，不读最佳实践文档 | 先读最佳实践文档，基于文档分析 |
| 优化后不验证，等待用户指出 | 优化后主动对照最佳实践文档验证 |
| 把技术选择当作禁止事项 | 技术选择放在专项文档，禁止事项放在 AGENTS.md |
| 重复其他文档中已有的内容 | 只链接，不重复 |

---

## 四、适用范围

本流程适用于所有文档优化任务，包括但不限于：
- AGENTS.md 优化
- README.md 优化
- WORKFLOW.md 优化
- 专项文档优化
- 项目文档结构调整

# 第二部分：文档变更驱动流程（强制）

## 五、职责边界说明

> - **具体操作流程**（如何创建/删除/调整目录）：见 `docs/DIRECTORY_STRUCTURE.md` 4.2-4.4节
> - **变更驱动动作**（变更后需要更新哪些文档、检查清单、联动关系）：见本章
> - 两者配合使用，先按 DIRECTORY_STRUCTURE.md 执行操作，再按本章执行驱动动作和检查

---

## 六、触发时机（自动触发，无需用户请求）

当 AI 执行以下任何操作时，必须自动触发本流程：
1. **新增文档**：创建任何新的 .md 文件或其他文档
2. **删除文档**：删除任何现有文档
3. **移动文档**：将文档从一个目录移动到另一个目录
4. **调整目录结构**：新增、删除、重命名目录，或调整目录层级
5. **优化文档内容**：大规模重构文档、拆分文档、合并文档

**用户提出需求时也自动触发**：
当用户提出需求（如"创建一个文档记录XXX"、"把这个内容整理成文档"、"这个文档不需要了"、"把这个文档移到那个目录"、"优化一下这个文档的结构"），AI 识别到该需求会导致文档变更时，必须自动触发本流程，不需要用户专门说"请执行文档变更驱动流程"。

**不需要用户专门请求**，这是 AI 维护文档时必须自动遵守的规则。用户请求"创建文档"、"删除文档"、"调整目录"等操作时，AI 必须自动执行本流程。

---

## 七、为什么需要联动机制

文档变更不是孤立的，一个文档的变化经常会驱动其他文档或目录结构的变化：

- **新增文档** → 需要更新文档地图、目录结构文档、可能需要新目录
- **删除文档** → 需要更新所有引用、文档地图、可能需要清理空目录
- **调整目录结构** → 需要更新所有路径引用、文档地图、目录结构文档
- **优化文档内容** → 可能需要同步更新其他文档中的引用或摘要

**没有联动机制的后果**：
- 文档地图过时，找不到新文档
- 引用关系断裂，点击链接404
- 目录结构文档与实际不一致
- 重复创建已有文档（因为不知道已存在）

## 八、文档变更类型与驱动动作

| 变更类型 | 必须执行的驱动动作 | 说明 |
|----------|-------------------|------|
| **新增文档** | 1. 更新 `docs/DOCUMENTATION_MAP.md`<br>2. 检查是否需要新目录（参考 DIRECTORY_STRUCTURE.md 4.2节）<br>3. 如果涉及目录变更，更新 `docs/DIRECTORY_STRUCTURE.md`<br>4. 在父文档或相关文档中添加链接<br>5. **评估是否需要新增ADR**（如果是重要的架构决策） | 新增文档前必须先检查是否已有类似文档 |
| **删除文档** | 1. 搜索所有引用：`grep -r "文档名" docs/ code/scripts/`<br>2. 更新所有引用（指向新位置或删除引用）<br>3. 更新 `docs/DOCUMENTATION_MAP.md`<br>4. 如果删除后目录为空，删除空目录<br>5. 如果涉及目录变更，更新 `docs/DIRECTORY_STRUCTURE.md`<br>6. **评估是否需要新增ADR**（如果是重要的架构决策） | 删除前必须检查引用关系 |
| **移动文档** | 1. 更新所有路径引用<br>2. 更新 `docs/DOCUMENTATION_MAP.md`<br>3. 更新 `docs/DIRECTORY_STRUCTURE.md`（如果涉及目录变更）<br>4. 验证所有链接有效<br>5. **评估是否需要新增ADR**（如果是重要的架构决策） | 移动等同于删除+新增，必须完整执行两边的动作 |
| **调整目录结构** | 1. 制定调整方案（调整前后结构、文件移动路径、引用更新清单）<br>2. 执行移动<br>3. 更新所有路径引用<br>4. 更新 `docs/DOCUMENTATION_MAP.md`<br>5. 更新 `docs/DIRECTORY_STRUCTURE.md`<br>6. 验证：`grep -r "旧目录名" docs/ code/scripts/`<br>7. **评估是否需要新增ADR**（目录结构重大调整必须记录ADR） | 调整前必须评估必要性（参考 DIRECTORY_STRUCTURE.md 4.4节） |
| **优化文档内容** | 1. 如果内容移到其他文档，更新原文档为链接<br>2. 如果其他文档引用了优化前的内容，同步更新<br>3. 更新 `docs/DOCUMENTATION_MAP.md` 中的文档说明（如果有变化）<br>4. **评估是否需要新增ADR**（如果是重要的架构决策，如文档分解） | 内容优化可能涉及职责边界调整 |

## 九、文档变更检查清单（强制执行）

执行任何文档变更后，必须按以下清单检查：

```
文档变更检查清单：
[ ] 1. DOCUMENTATION_MAP.md 已更新（新增/删除/移动文档）
[ ] 2. 所有引用关系已更新（grep 搜索验证）
[ ] 3. DIRECTORY_STRUCTURE.md 已更新（如果涉及目录变更）
[ ] 4. 空目录已清理（如果删除文档后目录为空）
[ ] 5. 所有链接有效（抽样验证）
[ ] 6. .gitignore 已检查（如果新增文件类型或目录）
[ ] 7. Git commit message 记录了变更内容和驱动动作
[ ] 8. 评估是否需要新增ADR（重要架构决策必须记录到 docs/project-management/decisions/）
```

## 十一、变更联动常见错误与纠正

| 错误做法 | 正确做法 |
|----------|----------|
| 新增文档后不更新文档地图 | 新增后立即更新 DOCUMENTATION_MAP.md |
| 删除文档前不检查引用 | 先 grep 搜索所有引用，更新引用后再删除 |
| 调整目录后不更新路径引用 | 调整后 grep 搜索旧路径，更新所有引用 |
| 文档变更后不验证链接 | 变更后抽样验证链接有效性 |
| 忘记检查 .gitignore | 文件和目录有变化时必须检查 .gitignore |
| 只变更文档，不更新目录结构文档 | 涉及目录变更时必须同步更新 DIRECTORY_STRUCTURE.md |

## 十二、文档健康度检查清单

### 触发时机

| 触发方式 | 触发时机 | 执行内容 |
|---------|---------|---------|
| **自动触发** | 每次git提交前 | pre-commit hook 自动检查**仅机械项**（关联链接、类型标注、大文件、命名提示）；语义项不在内，不能替代大任务后的完整体检 |
| **自动触发** | 每个大任务完成后 | 执行完整的文档健康度检查 |
| **自动提醒** | 每月/每阶段完成后 | 提醒执行全面文档梳理 |
| **手动触发** | 用户要求检查时、发现问题时 | 按需执行检查 |

### 检查项与检查方法

| 检查类别 | 检查项 | 检查方法 | 问题处理 |
|---------|--------|---------|---------|
| **完整性** | 所有文档是否在DOCUMENTATION_MAP.md中有记录 | `grep -r "文档名" docs/DOCUMENTATION_MAP.md` | 缺失则补充到文档地图 |
| **完整性** | 新增文档是否有类型标注（文档类型/更新频率/维护者） | `head -10 文档名` | 缺失则补充类型标注 |
| **关联性** | 文档中的链接是否有效 | 抽样检查关键链接 | 失效则更新或删除 |
| **关联性** | 是否存在文档孤岛（没有被任何文档引用） | `grep -r "文档名" --include="*.md" .` | 孤岛则在相关文档中添加引用 |
| **结构** | 目录结构是否与DIRECTORY_STRUCTURE.md一致 | 对比实际目录与文档说明 | 不一致则更新文档或调整目录 |
| **结构** | 命名是否符合NAMING_CONVENTION（类型↔命名、中文分隔符） | `python3 code/scripts/check_naming_consistency.py --regression` | 不自洽则按NAMING整改；批量改名走L1，先出清单确认 |
| **结构** | 是否存在空目录 | `find . -type d -empty` | 空目录则删除 |
| **质量** | 是否存在重叠内容（两个文档讲同一件事） | 人工审查 + 关键词搜索 | 重叠则合并或明确分工 |
| **质量** | 文档是否超过500行且内容跨领域 | `wc -l 文档名` + 内容审查 | 超过则评估是否需要分解 |
| **质量** | **内容精简度：是否有"正确的废话"、冗余段落、重复说同一件事** | 逐段审查：每段是否有独立信息增量；删除后是否影响理解 | 有则删除冗余段落，合并重复内容 |
| **质量** | **内容专业度：术语是否一致、表述是否准确、是否有AI套话/模板化表达** | 审查：术语与 ADR/规范一致；无"在当今快速发展的时代"类套话；结论有依据 | 有则修正术语、删除套话、补充依据 |
| **质量** | **结构清晰度：标题是否反映内容、章节层级是否合理、是否有空标题/空章节** | 审查：### 叶子节下无正文则为空标题（如"计算/综合大题（0道大题、0个小问）"必须删）；标题与内容匹配 | 有空标题则删除；标题不匹配则修正 |
| **维护** | .gitignore是否合理（新增文件类型时检查） | 审查.gitignore内容 | 不合理则更新 |
| **维护** | 核心文档（README/AGENTS/WORKFLOW）是否最新 | 对比实际情况与文档内容 | 过时则更新 |
| **维护** | **TASK_STATUS.md是否最新**（任务状态是否与实际一致） | 对比最后更新时间与最近的任务变更，检查任务进度是否准确 | 过时则立即更新，确保任务状态与实际一致 |

### 检查流程

```
触发文档健康度检查
    ↓
1. 完整性检查（文档地图、类型标注）
    ↓
2. 关联性检查（链接有效性、文档孤岛）
    ↓
3. 结构与命名检查（目录结构一致性、空目录；跑 check_naming_consistency.py 查类型↔命名）
    ↓
4. 质量检查（重叠内容、大文档分解）
    ↓
5. 维护检查（.gitignore、核心文档更新）
    ↓
发现问题
    ↓
评估问题严重程度
    ↓
严重问题 → 立即修复
一般问题 → 记录到待优化项，后续修复
    ↓
按需生成检查报告（过程件落 `data/_workspace/<course>/task-reports/`、不入库；验证默认并入任务报告、不单独成文；对话内体检且结论已落回活文档则不必留过程报告，见 PROJECT_STRUCTURE_MAINTENANCE 1.2）
    ↓
按 git-workflow 8.3 分场景提交（治理等用户验收，日常及时 commit，push 按约定）
```
