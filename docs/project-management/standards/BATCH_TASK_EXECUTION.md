# 大任务执行状态记录与异常恢复机制

> **文档类型**：Governance（治理规范）
> **更新频率**：规范变更时
> **维护者**：AI自动维护+用户审核
> **读者**：AI代理

> 本文档定义大任务（如批量处理多个讲次的完整流程）的执行状态记录方法、异常恢复机制和触发机制，确保任务遇到异常或停止后能够快速恢复，不丢失进度。

---

## 一、为什么需要这个机制

### 1.1 问题背景

- 大任务涉及多个讲次（N 个，实际数量以官方 syllabus 与该课 workspace 的 manifest 为准），每个讲次要走固定步骤（建目录→下载→压缩→验证→上传→转写→OCR→知识库→做题，步骤划分以 WORKFLOW.md 为准）
- 任务执行过程中可能遇到异常（网络中断、工具报错、用户中断、系统重启等）
- 如果没有详细的执行状态记录，恢复任务时需要从头开始，浪费大量时间
- 仅凭对话记忆不可靠，必须依赖文档记录

### 1.2 核心原则

- **检查点机制（Checkpointing）**：每完成一个步骤就保存状态，异常后从检查点恢复，不从头开始
- **信息可追溯**：计划表、状态表、问题表三张表，让所有信息可追溯
- **进度闭环**：记录→监控→预警→纠偏→固化，形成完整闭环

## 二、大任务执行状态记录模板

### 2.1 记录位置（分层）

**单门课的大任务状态记录在该课工作区 `data/_workspace/<course>/`（gitignore、不入库）**，通常是 `tickets/`（工单与实时进度）+ 批次状态文件；它是该课大任务执行状态的唯一来源。

- 单课大任务（批量处理 >3 个讲次、多工具链、预计 >1 小时）都必须在该课 workspace 留检查点记录。
- `project-management/TASK_STATUS.md` 是**全局**台账，只更新该课的**指针级**状态（一句话 + 指向 workspace），不抄讲次明细表、不抄易变计数。
- 跨课 / 项目级的大任务才在 `TASK_STATUS.md` 体现；不存在全局唯一的 `BATCH_TASK_STATUS.md`（该课程级定格文件已于 2026-09-08 下沉 workspace 并删除）。

## 三、异常恢复机制

### 3.1 异常分类与处理

| 异常类型 | 严重程度 | 处理方式 | 恢复起点 |
|----------|----------|----------|----------|
| 网络中断 | 低 | 等待网络恢复后重试 | 当前步骤 |
| 工具报错 | 中 | 查看错误日志，按文档解决方案处理 | 当前步骤 |
| Playwright断开 | 中 | 自动刷新Token，重新连接 | 当前步骤 |
| 用户中断 | 低 | 记录状态，等待用户指示 | 当前步骤 |
| 系统重启 | 高 | 读取执行状态记录，重新连接所有工具 | 上一检查点 |
| 输出文件损坏 | 高 | 删除不完整文件，从该步骤重新开始 | 上一步骤 |

### 3.2 检查点（Checkpoint）设置

**每个讲次的每个步骤完成后都是一个检查点**：

1. **步骤级检查点**：每完成一个步骤（如下载完成），更新状态记录
2. **讲次级检查点**：每完成一个讲次的所有步骤，更新讲次状态表
3. **批量级检查点**：每完成5个讲次，生成进度摘要报告

### 3.3 异常恢复流程

```
发现异常 → 记录异常到问题记录表 → 保存当前状态 → 诊断异常原因 → 按解决方案处理 → 验证恢复成功 → 从检查点继续执行
```

**详细步骤**：

1. **发现异常**：工具报错、用户中断、系统提示等
2. **记录异常**：立即在"问题记录表"中记录时间、讲次、步骤、问题描述
3. **保存状态**：确认当前执行状态已保存到该课 `data/_workspace/<course>/` 的批次/工单记录
4. **诊断原因**：查看错误日志，按文档中的解决方案处理
5. **处理异常**：
   - 小问题：顺手修复，继续执行
   - 大问题：记录解决方案，等待用户确认后继续
6. **验证恢复**：确认工具连接正常、输出文件完整
7. **继续执行**：从当前步骤继续，不从头开始

## 四、触发机制（强制执行）

### 4.1 必须创建执行状态记录的场景

**满足以下任一条件时，必须在该课 `data/_workspace/<course>/` 创建批次/工单执行状态记录：**

1. 批量处理 >3 个讲次
2. 预计执行时间 >1 小时
3. 涉及多个工具链（Playwright + ffmpeg + FunASR + 飞书API等）
4. 用户明确要求"批量处理"、"全部完成"

### 4.2 必须更新状态记录的时机

| 时机 | 更新内容 |
|------|----------|
| 开始大任务前 | 创建执行状态记录，填写任务总览和讲次状态表 |
| 每完成一个步骤 | 更新步骤执行记录，标记为✅，记录完成时间和输出位置 |
| 开始新步骤时 | 更新当前步骤，标记为🔄，记录开始时间 |
| 遇到异常时 | 在问题记录表中记录异常，更新当前步骤状态为⚠️ |
| 异常恢复后 | 更新问题记录表状态为✅，更新当前步骤状态为🔄 |
| 每完成一个讲次 | 更新讲次状态表，标记为✅，更新总进度 |
| 大任务完成后 | 生成最终进度报告，归档执行状态记录 |

### 4.3 必须先读取执行状态记录的场景

**满足以下任一条件时，必须先读取该课 `data/_workspace/<course>/` 的批次/工单执行状态记录：**

1. 恢复之前中断的大任务
2. 用户说"继续"、"接着做"、"恢复任务"
3. 系统重启后继续任务
4. 不确定当前进度时

### 4.4 违反机制的后果

如果发现执行大任务时没有创建/更新执行状态记录，导致异常后无法恢复：

1. 立即停止当前操作
2. 创建/补全执行状态记录
3. 从最近的检查点继续执行
4. 将本次教训补充到本文档中

## 五、进度监控与预警

### 5.1 进度偏差预警

| 预警级别 | 触发条件 | 处理方式 |
|----------|----------|----------|
| 🟡 黄色预警 | 时间消耗60%，进度<50% | 重新评估剩余工作复杂度，考虑优化流程 |
| 🔴 红色预警 | 时间消耗90%，进度<80% | 申请额外资源或缩减非核心范围 |

### 5.2 进度统计指标

每次更新状态时，自动计算：

- **总进度**：已完成讲次 / 总讲次 × 100%
- **当前讲次进度**：已完成步骤 / 总步骤数 × 100%（步骤数以 WORKFLOW.md 为准）
- **平均每讲次耗时**：总耗时 / 已完成讲次
- **预计剩余时间**：平均每讲次耗时 × 剩余讲次
