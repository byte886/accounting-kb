# 项目 DAG：任务依赖、时长与并发规划

> 本文档是本项目的完整任务 DAG（有向无环图），用于总调度决策。
> 核心原则：**依赖关系决定顺序，实测数据决定并发度，事件驱动触发下一阶段。**
> 换课程时直接复用本文档结构，只需更新节点时长和并发度（需重新实测）。

## 三、并发策略（基于实测，非估算）

### 3.1 已验证的并发组合

| 组合 | 并发方式 | 实测结果 |
|------|---------|---------|
| 下载(IO) + OCR(1核) + 压缩(11核) | 三路并行 | ✅ 互不拖累，总吞吐最大化（昨晚已验证） |
| 转写 + 15章归并表(设计) | 并行 | ✅ 转写吃2核，设计不占CPU |
| 知识库生成(按章) | 并行 | ✅ AI API调用，非CPU瓶颈，可按章并发 |

### 3.2 已验证的"串行最优"任务

| 任务 | 为什么不能并发 | 实测数据 |
|------|--------------|---------|
| FunASR 转写 | 内存带宽+cache争用，单进程已吃2核 | 1并发18.5x > 6并发14.3x > 3并发10.1x |
| x265 压缩 | 单实例已吃11核，开第二个无收益 | 全局1个speed10.4x，第二个总吞吐不增 |
| 抓HLS key | 同一Chrome一次一个播放标签 | 多标签hls worker互相干扰，拟人低频 |

### 3.3 并发度选型原则（换任务/换环境时复用）

1. **先跑单进程基线**：记录 CPU 占用、rtf/速度、单任务耗时
2. **逐步加并发**：2→3→6，每个稳定 3 分钟后采样
3. **对比总吞吐**：`总吞吐 = 并发数 × 单进程速度`，不是看单进程
4. **选总吞吐最高的**：若串行最高则串行（反直觉但常见）
5. **详见**：[parallel-processing-guide.md](performance/parallel-processing-guide.md)

## 四、阶段间触发条件（事件驱动）

| 触发事件 | 监听方式 | 触发动作 |
|---------|---------|---------|
| 39个 video.mp4 全部生成 | 60秒轮询计数 | 启动转写（节点7） |
| 39个 transcript.md 全部生成 | 60秒轮询计数+完成标记 | 启动知识库生成准备（节点9，需先确认节点8完成） |
| 15章知识拆解+考试指导全部生成 | 60秒轮询计数 | 启动知识库验证（节点10） |

> 监听脚本：`code/scripts/pipeline/watch_stage_done.sh`，零依赖，空窗最多60秒。
> 替代人工30分钟巡检，消除"任务已完成但总调度未发现"的空窗。

## 五、Fan-In 节点说明

**节点9（知识库生成）是 Fan-In**：必须等 5(OCR) + 6(线B采题) + 7(转写) + 8(组↔知识点映射) 全部完成才能启动。
- 8 不占 CPU，应在 7（转写）进行期间提前完成，避免 7 完成后空等 8

## 六、换课程复用指南

1. 先用 `fetch_user_space_courses.js` 拉账号课程、建 `config/courses/<key>.json` 课程 profile（课程参数化与并行工具收敛见 [parallel-toolkit-design.md](guides/parallel-toolkit-design.md)），再复制本文档更新节点 ID 与时长
2. **必须重新实测**的节点：视频压缩时长（不同课程视频时长不同）、转写并发度（换机器/换模型时）、下载时长
3. **可直接复用**的：DAG 结构、依赖关系、并发策略原则、监听脚本
4. 新课程若有新任务类型（如直播课、直播回放），新增节点并补充依赖边
