# 任务规划与并行调度方法论

> 沉淀自高顿 CPA 税法自动化项目的末期知识库原料补齐阶段（2026-09）。
> 适用场景：多阶段、多子任务、CPU/IO 混合的长流水线项目的任务规划与并发调度。
> 核心原则：**依赖关系定顺序，实测数据定并发，事件驱动触发衔接，总调度实时决策。**

## 一、四条核心原则

### 1. 大任务必须完整拆解为 DAG

- 任何大任务先拆解为子任务节点，标注依赖关系（有向无环图 DAG）
- 三种依赖模式：
  - **Linear Chain**：A→B→C（顺序依赖，如下载→压缩→转写）
  - **Fan-Out**：一个任务完成后触发多个并行下游（如下载完成→OCR+压缩并行）
  - **Fan-In**：多个上游全部完成后才触发一个下游（如 OCR+转写+采题+归并表→知识库生成）
- 每个节点必须标注：任务名、依赖、预估时长、资源类型（CPU/IO/API/设计）、最优并发度、状态
- 产出物：`docs/development/project-dag.md`

### 2. 除依赖外，必须评估任务时长并按需测试

时长评估分三档，**不是所有任务都要测试**：

| 档位 | 适用场景 | 方法 | 本项目案例 |
|------|---------|------|-----------|
| 经验估算 | 任务特性已知、历史数据可复用 | 凭经验/历史数据估 | 讲义下载（CDN IO，约5分钟）、OCR（1核，约2小时） |
| 小样本测试 | 任务特性不确定、测试成本低但价值高 | 跑1-2个样本测时长和资源占用 | FunASR转写并发度选型（测1/2/3/6并发）、x265压缩并发（测1vs2实例） |
| 历史数据复用 | 同项目/同环境已跑过同类任务 | 直接用历史数据 | 视频下载（已跑39讲，单讲约1.5分钟） |

**关键判断**：测试本身是否浪费时间？
- 测试成本低（几分钟）但影响大（决定并发度→影响总时长数小时）→ **必须测**
- 测试成本高或经验足够可靠 → **不测，直接估算**

### 3. 总调度必须实时调度，任务完成即通知

- **静态调度**（预分配任务到worker）：负载不均，快worker空闲等慢worker
- **动态调度**（共享任务队列+worker完成即取下一个）：天然负载均衡
- **事件驱动**（任务完成触发事件→总调度立即安排下游）：消除轮询空窗

本项目落地：
- 阶段内：`xargs -P N` 做动态调度（内核级，无竞态，子进程退出即启动下一个）
- 阶段间：`code/scripts/pipeline/watch_stage_done.sh` 做事件监听（60秒轮询产物数量，达到预期写标记文件，空窗≤1分钟）
- 总调度：agent 维护 DAG 状态，收到完成标记后检查下游依赖是否满足，满足即启动

**反例教训**：初期用人工30分钟巡检，压缩07:49完成但09:02才发现，空窗1小时13分钟。改用事件监听后空窗降到≤1分钟。

### 4. 并发度必须基于实测，不能凭核数估算

**Amdahl 定律**给理论上限 `1/(1-p+p/n)`，但实际受内存带宽、CPU cache、GIL（Python）等影响，CPU密集任务的最优并发度往往远低于物理核数。

**四步实测法**：
1. 跑单进程基线：记录 CPU 占用、rtf/速度、单任务耗时
2. 逐步加并发：2→3→6，每个稳定≥3分钟后采样
3. 对比**总吞吐**（不是单进程速度）：`总吞吐 = 并发数 × 单进程速度`
4. 选总吞吐最高的并发度；若串行最高则串行（反直觉但常见）

**本项目实测数据（FunASR SenseVoiceSmall，i5-13600KF 14核20线程）**：

| 并发数 | 单进程CPU | 单进程rtf | 总吞吐 | 相对串行 |
|--------|----------|----------|--------|---------|
| 1（串行） | 202% | 0.054 | 18.5x | **100%（最优）** |
| 2 | 186% | 0.17 | 11.8x | 64% |
| 3 | 175% | 0.30 | 10.1x | 55% |
| 6 | 177% | 0.42 | 14.3x | 77% |

结论：FunASR CPU推理串行最优，并发反而因内存带宽+cache争用降低总吞吐。

**不同任务类型的并发特性**：

| 任务类型 | 资源瓶颈 | 最优并发 | 判断依据 |
|---------|---------|---------|---------|
| FunASR转写 | CPU+内存带宽 | 串行 | 小模型推理受cache争用 |
| x265压缩 | CPU（11核/实例） | 全局1个 | 单实例已吃满多数核 |
| Vision OCR | CPU（1核/实例） | 1-2，可与压缩并行 | 单实例只吃1核 |
| 视频下载 | 网络IO | 20分片并发 | CDN静态资源，等同真实播放器 |
| 抓HLS key | Chrome单标签 | 串行 | 同一Chrome一次一个播放标签 |
| AI API调用 | 网络IO+API限流 | 按章并发 | 非CPU瓶颈，受API速率限制 |

## 二、任务队列实现教训

### 自建 flock 队列的竞态 bug

初版用 bash `flock -x 9` 自建任务队列，实测6个worker**全部重复取到同一讲**（队列只删了1行，6个进程都在处理同一任务）。原因：macOS bash 函数内 `exec 9<>lock; flock -x 9` 在多进程子shell下存在竞态，临界区未真正互斥。

### 正确方案：xargs -P（内核级并发管理）

```bash
# 生成待处理列表（每行一个任务）；process_one.sh 是"处理单条任务"的示例占位脚本名，落地时替换为本项目真实脚本
cat pending.txt | xargs -P 3 -n 1 bash code/scripts/process_one.sh
```

- 由内核管理并发和任务分发，**无竞态、自动负载均衡**（哪个进程空闲就拿下一个）
- `-P N` 指定并发数，`-n 1` 每次传一个参数
- 子脚本只需处理单个任务，无需关心队列

## 三、知识库组织：目标导向的双轨结构

**最终目标决定组织方式**，不是机械按任务堆。

以 CPA 考试知识库为例，目标是"通过考试"，内容天然分两类：
- **知识拆解**：学知识用（定义、分类、原则、税率表、计算方法）
- **考试指导**：应对考试用（做题技巧、易错点、记忆口诀、高频考点）

**C方案（混合，推荐）**：
- 按税种章组织每章的知识拆解+考试指导（学习阶段按章推进）
- 顶层只建一个总索引页《考试指导速查手册》（当应试宝典用，复习阶段直接刷）；《知识拆解总目录》不创建（飞书左侧目录树已承担导航，避免重复）
- 索引页在逐章内容完成后自动汇总生成

## 四、落地检查清单

启动一个多阶段长任务前，逐项确认：

- [ ] DAG 已画，每个节点标注依赖/时长/资源类型/并发度/状态
- [ ] Fan-In 节点的所有上游已识别，确保不会因某个上游未完成而卡住
- [ ] 可与主链路并行的任务已识别（如设计类、API类、IO类），安排在主链路进行期间提前完成
- [ ] CPU密集任务的并发度已实测（不是凭核数估）
- [ ] 阶段内用 xargs -P 动态调度（不是自建flock队列）
- [ ] 阶段间用事件监听（watch_stage_done.sh），不是人工长间隔巡检
- [ ] 总调度维护 DAG 状态，任务完成即检查下游并启动
- [ ] 换环境/换模型时，CPU密集任务的并发度必须重新实测
