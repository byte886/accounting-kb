# CPU 密集任务并发能力反向评估指南

> 适用场景：FunASR 转写、OCR、视频编码等本地 CPU 密集任务的并发度选型。
> 核心原则：**并发数 ≠ 吞吐提升，必须用实测数据反推最优并发，不能凭物理核数估算。**

## 一、方法论：反向评估四步

1. **先跑单进程基线**：记录单进程 CPU 占用、内存、rtf/速度、单任务耗时。
2. **逐步加并发**：从 2 开始，每次 +1（或跳测 3/6），每个并发度稳定运行 ≥3 分钟后采样。
3. **对比总吞吐而非单进程速度**：`总吞吐 = 并发数 × 单进程速度`。单进程速度必然随并发下降，关键看总吞吐是否上升。
4. **选总吞吐最高的并发度**：若串行总吞吐已最高，则串行就是最优（反直觉但常见）。

## 二、本项目实测数据（FunASR SenseVoiceSmall，i5-13600KF 14核20线程 128GB）

| 并发数 | 单进程 CPU | 单进程 rtf | 单进程速度 | 总吞吐 | 相对串行 |
|--------|-----------|-----------|-----------|--------|---------|
| **1（串行）** | 202% | **0.054** | 18.5x | **18.5x** | **100%（最优）** |
| 2 | 186% | 0.17 | 5.9x | 11.8x | 64% |
| 3 | 175% | 0.30 | 3.4x | 10.1x | 55% |
| 6 | 177% | 0.42 | 2.4x | 14.3x | 77% |

**结论：FunASR CPU 推理串行最优。** 单进程已吃满 2 核，多加进程因内存带宽 + CPU cache 争用导致单进程 rtf 非线性恶化（2 并发降到 1/3，3 并发降到 1/5.5），总吞吐不升反降。

## 三、不同任务类型的并发特性（本项目已验证）

| 任务类型 | 资源瓶颈 | 最优并发 | 说明 |
|---------|---------|---------|------|
| FunASR 转写 | CPU + 内存带宽 | **1（串行）** | 小模型推理受 cache 争用，并发反降 |
| x265 视频压缩 | CPU（11核/实例） | **1（全局单实例）** | 开第二实例总吞吐不增反降 |
| macOS Vision OCR | CPU（1核/实例） | **可与压缩并发** | 单实例只吃 1 核，压缩之余可跑 1–2 个 |
| 视频下载/解密 | 网络 IO | **可并发（20 分片）** | CDN 静态资源，等同真实播放器缓冲 |
| 抓 HLS key | Chrome 单标签 | **必须串行** | 同一 Chrome 一次一个播放标签，拟人低频 |

## 四、任务队列实现教训

### 自建 flock 队列的竞态 bug

初版 `transcribe_parallel.sh` 用 bash `flock -x 9` 自建任务队列，实测 6 个 worker **全部重复取到同一讲**（队列只删了 1 行，6 个进程都在处理 03 讲）。原因：macOS bash 函数内 `exec 9<>lock; flock -x 9` 在多进程子 shell 下存在竞态，临界区未真正互斥。

### 正确方案：xargs -P（内核级并发管理）

```bash
# 生成待处理列表（每行一个任务）；process_one.sh 是"处理单条任务"的示例占位脚本名，落地时替换为本项目真实脚本
cat pending.txt | xargs -P 3 -n 1 bash code/scripts/process_one.sh
```

- xargs 由内核管理并发和任务分发，**无竞态、自动负载均衡**（哪个进程空闲就拿下一个）
- `-P N` 指定并发数，`-n 1` 每次传一个参数
- 子脚本只需处理单个任务，无需关心队列

## 五、通用判断流程

1. 这个任务是 CPU 密集还是 IO 密集？
   - IO 密集（下载、上传、API 调用）：可高并发，受网络/接口限流约束
   - CPU 密集：必须实测，不能假设"核多就多开"
2. CPU 密集任务单进程吃几核？
   - 吃满多核（x265 吃 11 核）：全局 1 个实例
   - 吃 1–2 核（FunASR、OCR）：先实测 2/3 并发总吞吐，再决定
3. 并发后单进程速度是否线性下降？
   - 线性下降（总吞吐持平）：并发无收益，用串行
   - 超线性下降（总吞吐下降）：串行最优
   - 亚线性下降（总吞吐上升）：可增加并发

## 六、换环境/换模型时复用

- 换机器（不同 CPU/内存）：必须重新跑四步评估，不能直接套用本项目结论
- 换模型（如更大的 ASR 模型、Whisper）：单进程 CPU 占用和 cache 争用特性不同，重新评估
- 换任务类型（如本地 LLM 推理）：参考本方法论，但 GPU/显存约束不同
