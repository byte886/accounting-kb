# 长任务守护与主动通知指南

> 适用场景：网盘批量上传、视频转写、OCR、批量下载等**单次运行超过 8 分钟**的长任务。
> 核心原则：**不让 AI 轮询等待，用系统级守护进程自动续跑，完成时主动通知。**

## 一、问题背景：为什么不能直接用后台任务

AI 工具的 `Bash(run_in_background=true)` 后台任务存在约 **8 分钟超时限制**，到时间会被系统杀掉。对于需要数小时的任务（如 12G 视频上传），直接后台跑会被反复终止，AI 只能定期检查并手动重启——这是"轮询"，消耗轮次且依赖 AI 在线。

## 二、守护器范式（推荐）

```text
nohup 守护器（PPID=1，系统 init 接管，AI 会话结束也不影响）
  └─ while 循环：
       1. 执行任务脚本（断点续传，done 标记跳过已完成项）
       2. 执行完成检测命令
          ├─ 全部完成 → macOS 系统通知 → exit 0
          ├─ 连续 N 轮进度无变化 → 异常通知 → exit 1
          └─ 否则 sleep 5 秒，进入下一轮
```

### 三个关键机制

| 机制 | 实现 | 作用 |
|------|------|------|
| 系统级脱离 | `nohup ... & disown`，PPID 变为 1 | 不受 AI 会话 8 分钟超时影响 |
| 断点续传 | 任务脚本对每个完成项写 `.done` 标记，重跑自动跳过 | 被终止后从断点继续，不重复劳动 |
| 主动通知 | `osascript display notification` | 完成/异常时 macOS 弹窗，无需 AI 轮询 |

## 三、使用方法

### 3.1 任务脚本必须支持断点续传

任务脚本对每个工作单元（如一个讲目录）完成后写标记文件：

```bash
DONE_DIR="logs/xxx_done"
if [ -f "$DONE_DIR/单元名.done" ]; then
  echo "[跳过] 已完成"
  return 0
fi
# ... 执行工作 ...
echo "OK 单元名" > "$DONE_DIR/单元名.done"
```

### 3.2 用守护器启动

```bash
nohup bash code/scripts/run_supervised.sh <任务名> \
  "<单次执行命令>" \
  "<完成检测命令>" \
  > logs/supervisor_<任务名>.log 2>&1 &
disown
```

**示例（网盘视频上传，39 个讲）**：

```bash
nohup bash code/scripts/run_supervised.sh videos \
  "bash code/scripts/sync_raw_resources.sh videos 2" \
  "test \$(find logs/raw_done -name 'videos_*.done' | wc -l | tr -d ' ') -ge 39" \
  > logs/supervisor_videos.log 2>&1 &
disown
```

### 3.3 验证守护器已脱离 AI 会话

```bash
ps -o pid,ppid,command -p <守护器PID>
# PPID 应为 1（系统 init 接管）
```

### 3.4 随时查进度（code/scripts/progress.sh）

守护器在系统层运行，进度随时可查、只读不影响任务：

```bash
bash code/scripts/progress.sh
```

一屏输出所有后台长任务的：进度条与百分比、守护器存活状态、**实时速率 / 平均单耗 / ETA 完成时刻**、正在处理的工作单元、最近日志。示例：

```text
📹 视频上传网盘
   [██████████████░░░░░░░░░░░░░░░░] 48% (19/39)
   状态: 🟢 守护器运行中
   速率: 2.9 MB/s（并发2合计，单路 1.5）
   均个: 321MB，单个传 3.7 分钟，并发下均 1.8 分钟完成1个
   剩余: 6.2G，预计还需 36 分钟，约 19:40 完成
```

**ETA 与均耗的算法（动态现算，非估算拍脑袋）**：取最近若干个 done 标记的时间跨度和这些工作单元的实际大小，算出并发合计速率与单路速率，再用剩余总量 ÷ 合计速率得 ETA；每次查询都按最新速率重算，网络变化自动修正。新增一类长任务时，在脚本中按同样模式追加一段即可。

## 四、注意事项

1. **完成检测用 `find` 不用 `ls glob`**：文件名含中文/特殊字符时，`ls dir/prefix_*.done` 在某些 shell 环境下可能匹配失败返回 0（macOS BSD `seq 1 0` 也会错误输出，循环画进度条时需先判 `>0`）；`find dir -name 'prefix_*.done'` 更稳定。
2. **stall 检测**：守护器连续 3 轮（默认）进度无变化会判定异常并通知，避免任务卡死却无人知晓。
3. **并发任务也可守护**：任务脚本内部用 `xargs -P N` 并发（见 [parallel-processing-guide.md](parallel-processing-guide.md)），守护器只管"整批是否全部完成"。
4. **通知声音**：`sound name "Glass"`，可在系统设置中更换。
5. **AI 会话恢复后查进度**：优先 `bash code/scripts/progress.sh`；只看单个任务可 `tail logs/supervisor_<任务名>.log` + `find logs/xxx_done -name '*.done' | wc -l`，不需要等待。

## 五、适用场景清单

| 场景 | 单次耗时 | 工作单元 | done 标记 |
|------|---------|---------|-----------|
| 网盘批量上传 | 数小时 | 每个讲目录 | `logs/raw_done/` |
| FunASR 批量转写 | 数十分钟 | 每个视频 | 转写完成的 `.md` |
| OCR 批量识别 | 数十分钟 | 每个 PDF | OCR 输出文件 |
| 批量 API 同步（飞书） | 数分钟 | 每个节点 | `logs/wiki_done/` |
| 视频批量下载/压缩 | 数小时 | 每个视频 | 输出文件存在即完成 |

## 六、与"子任务主动上报"的关系

- **守护器**：解决"AI 会话超时导致任务被杀"的问题，是**进程级**保障。
- **子任务主动上报**：解决"总调度及时安排新任务"的问题，是**调度级**设计。
- 两者互补：守护器保证任务不中断，主动上报保证调度不等待。定期检查仅作为异常兜底，不是主要进度来源。

## 七、AI 自动接续：定时唤醒 + 临门一脚（标准范式）

### 7.1 为什么需要它

守护器（nohup，PPID=1）脱离 AI 会话独立运行，**无法反向叫醒 AI**：AI 是请求-响应模式、没有入站回调接口，系统层进程完成时只能弹 macOS 通知给人，AI 看不到。因此"任务完成 → AI 自动推进下一步"必须靠**定时唤醒**补齐，不能依赖用户回来戳。

### 7.2 轮询的固有延迟（必须认知）

固定间隔 N 分钟的定时唤醒是"到点触发"：任务在一次唤醒后 1 秒完成，也要等下一次唤醒才被发现，**最坏延迟 ≈ 一个间隔，平均 ≈ 半个间隔**。纯轮询无法做到"完成零延迟"（事件驱动需要入站回调，当前环境不具备）。

### 7.3 分层调度：粗粒度定时 + 临门一脚（推荐）

| 阶段 | 机制 | 发现延迟 |
|------|------|---------|
| 任务主体（数十分钟~数小时） | `create_cron_job` 周期唤醒 AI，查 progress，**没完成即结束本轮** | 一个间隔（空查秒回，成本极低） |
| 临近完成（某次唤醒发现 ETA < 1 个间隔） | AI **不再结束本轮**，用 Wait 在当前轮阻塞等到完成 | **零延迟立即接续** |
| 全部结束 | AI 推进下一步，并 `delete_cron_job` 自清理定时任务 | — |

要点：
1. **间隔选择**：空查几乎零成本，1 小时级任务用 3 分钟、数小时级（转写）用 20–30 分钟。
2. **临门一脚**：长跑期多等一个间隔毫无感；收尾期靠当前轮 Wait 短等实现零延迟，兼顾省轮次与快衔接。
3. **机械步骤前置脚本化**：完成后的纯机械校验（文件计数、对平）写成脚本由守护器流水线先跑，AI 唤醒后直接读结果，只做需要判断的决策。
4. **自清理**：任务结束必须删除对应定时任务，避免空转唤醒。
5. **不依赖人**：macOS 弹窗只是给用户的辅助提醒；AI 接续只依赖定时唤醒 + done 标记，用户无需通知 AI。

### 7.4 标准启动序列

```text
1. 确认任务脚本支持断点续传（done 标记）
2. nohup 启动守护器（进程级，PPID=1）
3. create_cron_job 挂周期唤醒（query 写清：查 progress→未完成静默/临近则 Wait→完成则推进并自删本任务）
4. AI 结束当前轮，不阻塞用户
```

### 7.5 认证型长任务：进程退出自动恢复 + token 自愈（会计课实证）

需要登录态的长跑任务（如批量做题），除 7.3 的"查进度"外，定时唤醒还应承担**自动恢复**职责，不能只报告"进程已退出"：

1. **进程退出自动拉起**：唤醒时若守护进程不存在且任务未完成（日志无完成标记），先定位退出原因，再用 `nohup ... >> 日志 2>&1 &` **追加方式**重启（`>>` 而非 `>`，避免覆盖历史日志）；脚本须支持断点续跑，已完成项快速跳过。
2. **token 失效自愈优先于重启**：若退出原因是登录态失效（高顿业务码 553649434，HTTP 200 但业务层"登录超时"），先刷新凭证再重启，否则重启后仍会立刻失败。刷新分两级：任务脚本内部捕获失效码自动刷新重试（首选，见 exam-workflow）；定时唤醒兜底时若脚本无内置自愈，先手动跑刷新脚本再拉起进程。
3. **重试上限与升级**：同一故障自动恢复最多 2 次；2 次后仍失败，停止重试、记录详细错误并明确交用户介入（如浏览器登录态也丢失、需验证码）。
4. **已正常完成的不重启**：日志已有完成标记（如"全部章节处理完成"）属正常退出，不要误拉起；已知的非阻断遗留问题（如某子步骤待单独修复）只报告、不在本任务里顺手处理。

> 教训（2026-09 会计课）：定时巡检一度只报告"进程退出、待重启"，加上 `findJwt` 按文件名排序导致新 token 被旧文件遮蔽，结果 token 失效后 170 张卷全部失败、任务停滞数小时。修复=排序改 mtime + 脚本内 token 自愈 + 巡检自动拉起，三层缺一不可。

### 7.6 批量做题：进程级守护优先于定时巡检（2026-09-08 升级）

7.5 的"定时唤醒拉起"对做题仍有最多一个间隔的固有延迟，AI 不在线时任务一直干等。批量做题改为直接用守护器在**进程层闭环**：`cdp/run_papers_supervised.sh <profile>` 让 `run_supervised.sh` 每轮"先 `refresh_inventory` 从平台回查重建 audit → 再 `batch_redo_papers --go`"，redo 静默退出后 5 秒自动续跑、只补平台仍未达成的卷，PPID=1 脱离 AI 会话，完成/卡死发 macOS 通知。要点：

1. **顺序铁律**：重启做题前必须先 refresh 重建 audit。redo 不回写 audit，直接重启会按启动时的旧 audit 从 `[1]` 重做已满分卷——这正是"永远前几十张"死循环的根因。
2. **进度标量取平台已达成数**（inventory 里满分+平台最优张数，单调不减），不要用 redo 日志里的 `[N/M]` 序号（每轮重置）；连续 3 轮不增长判异常，可识别"个别卷客观无法满分被反复啃"。
3. **三层定位**：脚本内 token 自愈（首选，redo 已内置捕获 553649434 自动刷新）→ 守护器进程级续跑（主保障，不依赖 AI/定时）→ 定时唤醒（仅当需要 AI 在全部完成后自动推进下一阶段时才挂；纯保活不需要，可停用）。
4. `run_supervised.sh` 为此泛化出**可选第 4 参「进度标量命令」**，支持不产 `.done` 标记的任务；videos 等老任务不传第 4 参，行为完全不变（向后兼容）。
5. **"通知到人"走 AI、不走 Mac 弹窗（2026-09-08 定）**：做题线设 `SUPERVISE_NO_OSASCRIPT=1` 关闭 osascript 屏幕弹窗，守护器只把终态写成日志里的 `[NOTIFY] ✅/❌` 行；由 15 分钟定时任务（平台最小间隔 900s）唤醒 AI 读终态 → 自动做终态核对 / 推进冲刺卷 → 在豆包通知用户。进程不会因这 15 分钟而停（守护器一直续跑），只是 AI 接手动作最长滞后一个间隔。守护器用 `caffeinate -i` 包裹防 Mac 空闲睡眠（`pmset -g assertions` 可见 PreventUserIdleSystemSleep）。
