# 问题与 BUG 跟踪（ISSUES）

> **文档类型**：Active（全局活态台账）
> **更新频率**：跨课/机制级问题发现或解决时
> **维护者**：AI 自动维护 + 用户审核
> **读者**：AI 代理（收到问题查询、排障时读取）和人类

## 职责边界（先读）

- **这份文档装什么**：**跨课 / 机制级**的问题、BUG、风险及其生命周期（open → closed）与解法。回答的是"**这个项目有哪些共性的坑、怎么解的**"。
- **谁在用**：AI 被问"有什么问题 / bug"、动手前排障先查是否已知时读；修复后回填解法。用户用它看遗留风险。
- **什么时候写**：发现影响**不止一门课**、或属于脚本/流程/机制本身的缺陷时登记为未解决；解决后移入已解决区并记解法。
- **绝不装什么（边界）**：
  - **只影响某一门课 / 某张工单的一次性问题**，进该课 `data/_workspace/<course>/tickets/BUG_BACKLOG.md`（过程台账，不入库），**不提升到这里**；只有当它被判定为"换课还会踩"的机制问题时，才把共性结论提炼到本文件或 ADR/OKF。
  - 当天易变的报错、日志、进度异常不登记（看 workspace 日志即可）。
  - 任务进度状态在 [TASK_STATUS.md](TASK_STATUS.md)，本文件只记问题本身，用 ID 与之关联，不重复描述进度。
- 已解决问题保留最近 10 条；更早的共性结论若有长期价值，提炼进 ADR/OKF 后即可从这里淡出。

## 四、问题处理流程

### 4.1 发现新问题时

1. 在本文档"未解决问题"部分添加新条目，分配ID（I-XXX）
2. 评估严重程度（高/中/低）和优先级
3. 如果是小问题（文档链接错误、文件名不对、简单脚本bug），顺手修复
4. 如果是大问题（流程变更、架构调整、新增功能），先和用户讨论，确认方案后再执行
5. 修复后，将条目移到"已解决问题"部分，记录解决时间和解决方案

### 4.2 问题严重程度分类

| 严重程度 | 定义 | 处理方式 |
|----------|------|----------|
| 🔴 高 | 阻塞核心流程、数据丢失、安全问题 | 立即处理，优先于其他任务 |
| 🟡 中 | 影响效率、功能受限、需要 workaround | 计划处理，在当前阶段完成 |
| 🟢 低 | 体验优化、文档完善、非核心功能 | 后续维护中逐步处理 |

### 4.3 问题来源

- 用户反馈
- AI执行任务时发现
- 任务报告/验证留痕中发现
- 定期项目检查时发现

## 五、维护规则

1. **发现新问题时**：必须在本文档中记录，不能只在对话中提及
2. **问题解决后**：必须移到"已解决问题"部分，记录解决时间和解决方案
3. **定期清理**：已解决问题保留最近10条，更早的移到历史归档
4. **AI查询时**：收到用户"有什么问题"、"有哪些bug"等查询时，必须先读取本文档，按标准格式响应
5. **与TASK_STATUS关联**：如果问题与特定任务相关，在TASK_STATUS.md中也标注问题ID
